Automatic Agentic discovery
This project is about making a generic framework/process for making adaptors/clients for web services / web applications so that LLM agents and in turn scripts can use web services and interact with them. The main problem is that most web applications are intended for humans. I.e. the web applications were built with a focus on “looking pretty”, of the mind set of their creators of how they thought their “customers” would interact with the web page. A client intended for LLMs/scripts does not have the same constraints.  Its problem area is more around understanding how to make the existing API fit its need and understand how to operate the API in a correct manner as well as understanding the underlying problem - what an end user wants to do, what can be done with the web page/service and be the middle man for the end user to be more productive - buy products, get the overview, understanding what kind of things the LLM might NOT see (hidden knowledge, features). For these hidden features, the system must store expectations/uncertainties/rumors of functionality/products that might not be there. Similary, once we hear of such rumors, they must not be assumed to be correct until they have been verified. So, one part of the system is traversing a web page, REST/API services underneath. Documenting the visible & under the hood parts of the web page and store the sitemap of the web page, up to a certain depth. Note that “spamming” a site can be seen as a possible sign of intrusion, and having a backoff feature / taking some time for accomplishing the survey step can be benificial and should be a config parameter to the process. Authentication and personally sensitive is a problem we’ll have to solve - how do we pass on authentication information so that the system can work on behalf of the end user. How do we deal with the personal sensitive data and avoid sending that data to LLMs that potentially are “rogue”, how can we discern between rogue and personal secure LLMs? I’m thinking the LLMs available must be categorized and stored as property files so the end user can tweak alternatives / provide multiple options / subscriptions and possibly have a local “air gapped” LLM for processing sensitive personal/company data and keep those calls separate from the queries that are sent to “generic, possibly questionable” LLM’s that are good at performing tasks, but we can’t trust with sensitive data. Thus, we must categorize what kind of operations involve working with sensitive data and imply utilizing approved LLMs. Categorizing which steps are sensitive must be done in the early planning stage of the process, perhaps later also. The site map can be stored in a graph / .md structure - whatever feels correct for the intelligence gathering LLM. It will serve as the basis for further development. Intelligence gathering can be done at multiple stages and we must assume that we can gather contradicting information about a web page/service as time goes on. Especially if web pages are developed as time goes on, so the timestamp for when information was gathered is important. I propose using technology such as Playwright for gathering web traversal information, and it (or aligned tech) must gather UI/web imprints, so that we know how the UI looked like at the time it was gathered intelligence on, the API’s encountered and logs written. As part of the information gathering, performing ordering of products, gathering information about the products will be done, but beware that we will stop short of actually performing “destructive operations” - ordering or going through the payment part in the initial intelligence gathering. It might be that sites provide OpenAPI docs or similar, that we should gather and leverage in KCP. So, along with information about the web page, what it is about, what we can accomplish with it, we also need to gather information from outside context (web research probably) to gather more context. The prompter might have additional information about what this site is about and what we want to accomplish with the site. We especially want to know the APIs that we encounter - what they are about, data in, data out - examples, validations etc. After we have gathered the initial info. The information will thus be converted into “claude skills” that covers the different aspects of the site so that claude as an LLM has the information about the site to work with it, set up a new claude project and reference the skills we have made We will then set up a mirror KCP (Knowlege Context protoco https://github.com/Cantara/knowledge-context-protocol) site/files that will store the Agentic information so that a “generic” LLM+client can interact with the web site and build a client for accessing+tracerse the web pages and rest interface. We will then start building a REST client that can perform the tasks available to the web site. Verifying that we can do Proof of concepts against the web page - traversal and utilizing functionality on the web page (ordering, possibly submitting etc) It might be that prompts and skills are enough, but, this is up the process to find out what suffices. Note that each site must store what kind of operations are allowed to do - can we order products, can we traverse the web site - at which depth? How “slow” must we be on the web site and back off to avoid spamming/raising suspicion, I.e. be a good web citizen. What do we want to accomplish once we have set up these skills, site overview, context information, site specific configuration and API specs? With a KCP site (shadow or not)/landing page, we can use LLMs to operate for us against the web page. One use case is to make a client that users that can’t interact with web pages due to… being blind, having no hands - i.e. need to talk to a web page and interact with it through the LLM. Enterprice customers that need to do bulk operations - submit large orders, do integrations between two web sites and operate with data across multiple domains - fetch data from one site and put it into the other like a super user that needs to get an overview over the available data of multiple sites and enter LLM and super-user modified data to a third site. And it can be used by a security researcher as a basis for doing penetration testing, security scans, vulnerability scan etc on the basis of the functionality of the site. The overall point we are trying to create the basis here, is a system that we can put on multiple sites and create “projects” per site so that we can make agents work with the sites we create KCP information from. Along the way, we also want to have an evolving system that takes in the lessons learned and leverages it as time goes on. Most likely as skills that can be used across multiple sites. Over time, structuring information and comparing what we already know (skills) with new information.
