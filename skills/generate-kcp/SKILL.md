# KCP Artifact Generation

KCP manifests are **automatically generated** as Step 6 of the triage pipeline. This skill documents the format, how to evaluate output, and how to use KCP manifests.

## What is KCP?

KCP (Knowledge Context Protocol) is a structured metadata standard for making knowledge navigable by AI agents. "KCP is to knowledge what MCP is to tools." It produces a `knowledge.yaml` manifest that indexes knowledge units with intent, audience, load strategy, and dependency metadata.

Spec: https://github.com/Cantara/knowledge-context-protocol

## What Gets Generated

The pipeline produces both **content** and **manifest**:

| File | Role | Generated by |
|------|------|-------------|
| `knowledge.yaml` | KCP manifest — indexes all files | Deterministic (Step 6) |
| `CLAUDE.md` | Site orientation for agents | LLM (Step 5) |
| `README.md` | Human-readable project card | LLM (Step 5) |
| `sitemap.md` | Navigation model | LLM (Step 5) |
| `skills/*.md` | Site-specific skills | LLM (Step 5) |
| `apis/*.md` | API docs with confidence levels | LLM (Step 5) |
| `unknowns.md` | Unverified features/APIs | LLM (Step 5) |

## KCP Manifest Structure

```yaml
kcp_version: "0.29"
project: www.example.com
version: 1.0.0
updated: 2026-03-18
language: nb
indexing: read-only
units:
  - id: site-overview
    path: CLAUDE.md
    intent: "What is www.example.com and how should an AI agent interact with it?"
    scope: global
    audience: [agent, developer]
    hints:
      load_strategy: eager      # Load immediately
      priority: critical
  - id: skill-order-flow
    path: skills/order-flow.md
    intent: "How to order flow on www.example.com"
    scope: module
    audience: [agent]
    depends_on: [site-overview]
    triggers: [order-flow, order, flow]
    hints:
      load_strategy: lazy       # Load when triggered
      priority: supplementary
```

## Key KCP Concepts

### Load Strategy
- **eager**: Always load into context (CLAUDE.md, sitemap)
- **lazy**: Load only when relevant to task (skills, API docs)
- **never**: Don't load into LLM context (raw triage report JSON)

### Unit Types
- **knowledge**: Prose docs (CLAUDE.md, skills, unknowns)
- **schema**: Structured data (triage-report.json)
- **service**: API documentation (apis/*.md)

### Dependencies
Skills depend on `site-overview` — the agent should load CLAUDE.md before any skill.

### Triggers
Keywords that signal a skill should be loaded (e.g., `order`, `navigate`, `plan-trip`).

## Quality Checklist

After generation, evaluate:

- [ ] **knowledge.yaml** exists and is valid YAML
- [ ] All generated files are indexed as units
- [ ] `site-overview` has `load_strategy: eager` and `priority: critical`
- [ ] `triage-report` has `load_strategy: never` (too large for context)
- [ ] Skills have appropriate `triggers`
- [ ] `depends_on` chains are correct (skills → site-overview)

## How Other Agent Frameworks Use This

A non-Claude agent can:
1. Read `knowledge.yaml` to discover what knowledge exists
2. Load `eager` units immediately (site orientation + sitemap)
3. Based on user task, load `lazy` units matching triggers
4. Follow `depends_on` to ensure prerequisites are loaded
5. Skip `never` units (raw data) unless explicitly needed

This makes the triage output **framework-agnostic** — not just for Claude.
